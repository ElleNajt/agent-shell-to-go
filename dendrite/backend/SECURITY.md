# Security Model

## Threat model

agent-shell-to-go mirrors Emacs agent-shell conversations to a mobile app and allows sending messages back. The security boundary is your Tailnet: **all devices on the Tailnet are fully trusted**. There is no per-user authentication beyond Tailnet membership and a shared bearer token.

The Host header, Content-Type, Origin, and token protections exist to defend against browser-based attacks from the public internet (malicious websites, DNS rebinding, cross-origin requests). They do not protect against a malicious device on the Tailnet.

This means:
- This is designed for a single-user Tailnet
- Don't use this on a shared Tailnet where you don't trust every device
- If your Tailscale key is compromised, your agent conversations and controls are exposed
- The bearer token prevents casual access but is not a substitute for network isolation

## Architecture

```
Phone (React Native app)
  |
  | HTTP/WebSocket over WireGuard (Tailscale)
  |
  v
Go backend :8080 (bound to Tailscale IP only)
  |
  |-- POST /events/*           Emacs -> backend (agent lifecycle, messages)
  |-- GET  /agents             List active agents
  |-- GET  /agents/{id}/messages  Message history
  |-- POST /agents/{id}/send   Send message to agent (-> Emacs via WebSocket)
  |-- POST /agents/{id}/stop   Interrupt agent
  |-- POST /agents/{id}/permission  Respond to permission request
  |-- GET  /files/list         List files in project directory
  |-- GET  /files/read         Read file from project directory
  |-- GET  /ws                 WebSocket for real-time events
  |-- GET  /health             Health check (no auth)
  |
  | WebSocket (bidirectional)
  |
  v
Emacs (agent-shell-to-go-mobile.el)
  |
  | advice hooks on agent-shell
  |
  v
agent-shell buffers (Claude Code sessions)
```

## Security layers

### 1. Network binding (primary boundary)

The Go server binds exclusively to the Tailscale IP (auto-detected via `tailscale ip -4`). If Tailscale is unavailable, the server refuses to start (`log.Fatal`). This is the main security boundary — the server is never reachable from the public internet.

### 2. Bearer token authentication

All endpoints except `/health` require a valid bearer token. The token is:
- 32 bytes from `openssl rand -hex 32` (256 bits of entropy)
- Compared with `subtle.ConstantTimeCompare` (timing-safe)
- Passed via `Authorization: Bearer <token>` header
- For WebSocket upgrades (where headers are unreliable), accepted via `?token=` query parameter

The token is generated by `start.sh` and stored at `~/.dendrite/token`. The Emacs client reads it from this file. The mobile app stores it in AsyncStorage after manual entry.

**Limitation:** The WebSocket query parameter appears in server logs. This is acceptable for a Tailscale-only service where the logs are local.

### 3. Host header validation (DNS rebinding defense)

All requests pass through middleware that validates the `Host` header matches the Tailscale IP, `localhost`, or `127.0.0.1`. This blocks DNS rebinding attacks: after an attacker rebinds their domain to your IP, the browser sends `Host: evil.com` — which is rejected before any handler runs.

The middleware also sets security headers on all responses:
- `X-Frame-Options: DENY` — prevents clickjacking via iframes
- `Content-Security-Policy: frame-ancestors 'none'` — reinforces frame blocking
- `X-Content-Type-Options: nosniff` — prevents MIME-sniffing

### 4. CSRF protection (Content-Type enforcement)

State-changing requests (POST/PUT/PATCH) must have `Content-Type: application/json`. Browser form submissions can only send `text/plain`, `application/x-www-form-urlencoded`, or `multipart/form-data`. Since browsers cannot set `application/json` without a CORS preflight (which is rejected — OPTIONS returns 405), this blocks form-based CSRF without needing a separate CSRF token.

### 5. WebSocket origin rejection

The WebSocket upgrader rejects any request that includes an `Origin` header. Non-browser clients (Emacs `websocket.el`, React Native) don't send `Origin`. Browsers always do. This blocks malicious websites from opening WebSocket connections to the backend.

### 6. File access controls

The `/files/list` and `/files/read` endpoints restrict access to project directories of currently active agents. Protection includes:

- **Path traversal prevention:** `filepath.Clean()` canonicalizes paths to remove `../` traversal
- **Symlink resolution:** `filepath.EvalSymlinks()` resolves symlinks before validation, preventing symlinks inside a project that point outside it
- **Separator-aware boundary checking:** Path prefix checks use directory separator boundaries, so `/projects` cannot match `/projects-secret`
- **File size limits:** 1MB for text files, 10MB for images
- **Type restrictions:** Only known text and image extensions are served

### 7. Input validation

- Request bodies are limited to 1MB (`http.MaxBytesReader`) to prevent OOM
- SQL queries use parameterized placeholders — no string concatenation
- Message content is truncated to 200 characters for storage in the agents table

### 8. Generic error messages

Error responses return generic messages (`"access denied"`, `"not found"`, `"internal error"`). Detailed error information is logged server-side only. This prevents information disclosure about internal paths, database state, and system configuration.

## Known limitations and accepted risks

### Tailnet access + token = full access

Any device on the Tailnet with the bearer token has full access to read conversations, send messages to agents, stop/restart agents, and read project files. This is the intended security model — Tailscale provides the network boundary, the token provides the authentication layer.

### Token in WebSocket query parameter

WebSocket clients cannot reliably set HTTP headers during the upgrade handshake, so the token is accepted as a query parameter for `/ws`. This means the token appears in server logs and potentially in proxy logs. Since the service runs on a Tailscale network with local logs only, this is acceptable.

### Dynamic file access whitelist

The file endpoints use a dynamic whitelist based on currently active agents' `project_path` values from the database. This means:
- Files are only accessible while an agent session is open for that project
- If an agent closes, its project files become inaccessible
- Race condition: an agent could close between a file list and file read request

### No rate limiting

There is no per-token or per-IP rate limiting. An authenticated client could spam endpoints to cause resource exhaustion. SQLite's single-connection pool provides natural throttling, and the Tailscale boundary limits exposure.

### WebSocket broadcast retries

For critical events (`send_request`, `stop_request`), failed broadcasts are retried up to 3 times with 1-second delays. This is a best-effort delivery model — if no WebSocket client is connected, the event is lost.

## Test coverage

The test suite (`main_test.go`) includes:

- **Token authentication tests:** Valid token accepted, bad tokens rejected (missing, empty, incorrect), constant-time comparison, token via query parameter for WebSocket
- **DNS rebinding defense:** Host header validation for Tailscale IP, rejection of evil domains and localhost, IP prefix attack prevention
- **CSRF protection:** Content-Type enforcement on POST requests, form submission blocking, JSON requirement
- **WebSocket security:** Origin header rejection for browser-based hijacking
- **Path traversal prevention:** `../` normalization, symlink escape blocking, separator-aware boundary checking, prefix collision prevention
- **Security headers:** X-Frame-Options, CSP, X-Content-Type-Options on all responses
- **Attack simulations:** DNS rebinding read, cross-site form CSRF, WebSocket hijacking, path traversal via symlink, file access outside project boundaries
- **Input validation:** Body size limits, generic error messages (no internal path leakage)
